# 13. Compilers, Build Systems, Toolchains, Sysroots, and Cross Compilation

Large projects expose many commands—`clang`, `ld`, `meson`, `ninja`, `cmake`, `pkg-config`—that can look like one undifferentiated “build step.” They occupy different layers.

## 13.1 The build pipeline

A simplified C/C++ path is:

```text
source
    -> preprocessing
    -> parsing and semantic analysis
    -> compiler IR
    -> optimization
    -> target code generation
    -> assembly/object encoding
    -> relocatable object files
    -> linking
    -> ELF executable/shared library
```

A compiler driver such as `clang` can orchestrate several of these stages and invoke the linker.

## 13.2 Preprocessing

C-family preprocessing handles directives such as:

```c
#include <foo.h>
#define VALUE 42
#ifdef FEATURE
#endif
```

`#include` makes declarations and definitions from headers visible to compilation. It does **not** by itself link the implementation library.

This distinction is fundamental:

```text
header
    -> compile-time interface declaration

library
    -> implementation and symbols
```

## 13.3 `-I`, `-L`, and `-l`

```text
-I/path/include
    -> header search path

-L/path/lib
    -> library search path at link time

-lfoo
    -> request libfoo according to linker naming rules
```

Failure signatures map to stages:

```text
foo.h: No such file
    -> compile/header discovery problem

undefined reference to foo
    -> link-time symbol resolution problem

libfoo.so.1 not found at startup
    -> runtime dynamic-loader discovery problem
```

## 13.4 Translation units and object files

Each C/C++ source file plus its preprocessed include context forms a translation unit.

```text
main.c + headers -> main.o
foo.c + headers  -> foo.o
bar.c + headers  -> bar.o
```

Then:

```text
main.o + foo.o + bar.o + libraries
    -> linker
    -> executable
```

Object files make incremental builds possible: changing one source file need not recompile every unrelated translation unit.

## 13.5 Frontend, IR, optimizer, backend

A modern compiler architecture can be understood as:

```text
language frontend
    -> language semantics
    -> intermediate representation
    -> optimizer
    -> target backend
    -> machine instructions
```

This separation allows multiple frontends and multiple target backends to share infrastructure.

The project implication: a compiler running as a bionic-native host tool can still be configured to generate code for a glibc target world if headers, libraries, linker behavior, and target configuration are controlled coherently.

## 13.6 Assembler and linker

The assembler encodes assembly instructions and related metadata into object files.

The linker:

```text
resolves symbols
lays out sections/segments
assigns addresses
applies static relocations
creates dynamic-link metadata
produces executable or shared object
```

A compiler driver is usually safer than invoking `ld` manually because it knows startup objects, runtime libraries, and target-specific defaults.

## 13.7 Static and shared libraries

Static archive:

```text
foo1.o + foo2.o
    -> libfoo.a
```

At final link, needed object code can be incorporated into the executable.

Shared library:

```text
PIC objects
    -> shared link
    -> libfoo.so
```

The application can record a runtime dependency such as:

```text
DT_NEEDED libfoo.so.1
```

## 13.8 Build system versus compiler

A build system manages a dependency graph of commands.

It answers questions like:

```text
Which source files belong to this target?
Which generated files must exist first?
Which include paths and macros apply?
Which dependencies are optional?
What must rebuild after a change?
How can tasks run in parallel?
Where should install artifacts go?
```

The compiler only handles compilation/link-oriented tasks. It does not inherently understand the project’s complete build graph.

## 13.9 Make

Make models targets, prerequisites, and recipes.

Simplified:

```make
app: main.o foo.o
	clang main.o foo.o -o app

main.o: main.c
	clang -c main.c
```

The key idea is a dependency graph and incremental rebuild decisions.

## 13.10 Ninja

Ninja is designed as a fast low-level build executor. Large Ninja files are often generated by higher-level configuration systems.

Typical relationship:

```text
Meson/CMake/GN
    -> generate build graph
    -> Ninja executes compile/link/generator commands
```

Ninja is not a compiler and generally is not where high-level platform policy should be hidden manually.

## 13.11 Meson

A typical Meson workflow:

```text
meson.build files
    -> meson setup builddir
    -> dependency detection and configuration
    -> build graph
    -> Ninja backend execution
```

For Mesa, Meson options select major parts of the build graph:

```text
platforms
Vulkan drivers
Gallium drivers
KMD support
GLX/EGL mode
LLVM usage
```

Changing an option can change source selection, dependencies, generated configuration, and final ELF dependency shape.

## 13.12 CMake

CMake is a build-system generator/configuration system, not the C compiler itself.

A conceptual flow:

```text
CMakeLists.txt
    -> CMake configure/generate
    -> Ninja or Make backend files
    -> executor
    -> compiler/linker
```

When debugging, identify which layer produced the wrong decision: CMake configuration, backend graph, compiler flags, linker flags, or runtime loader behavior.

## 13.13 Autotools and `configure`

A traditional workflow:

```text
./configure
    -> feature/platform checks
    -> Makefile/config headers
    -> make
    -> make install
```

A configure test can compile and sometimes run small programs. This becomes important during cross compilation because a target binary may not be executable on the build machine.

## 13.14 `pkg-config`

`pkg-config` is a metadata query tool for development dependencies.

A `.pc` file can describe:

```text
prefix
include directories
library directories
link flags
version
private dependencies
```

Example:

```sh
pkg-config --cflags dbus-1
pkg-config --libs dbus-1
```

It is neither a package manager nor a runtime loader.

## 13.15 Why `.pc` files can contaminate cross/runtime builds

Suppose a Debian `.pc` file contains:

```text
prefix=/usr
libdir=/usr/lib/aarch64-linux-gnu
includedir=/usr/include
```

but the intended target world uses another prefix/sysroot.

The build can accidentally mix:

```text
bionic headers
glibc libraries
Debian metadata
project-local libraries
```

This can produce immediate build errors or, worse, a successful link followed by runtime incompatibility.

Therefore control:

```text
PKG_CONFIG_PATH
PKG_CONFIG_LIBDIR
PKG_CONFIG_SYSROOT_DIR
```

according to the build system and target design.

## 13.16 Toolchain

A toolchain is broader than one compiler binary.

It can include:

```text
compiler driver
assembler
linker
archiver
ranlib
strip
objdump/readelf-style tools
target headers
runtime libraries
sysroot
target configuration
```

The project’s glibc toolchain wrappers exist to make the target world explicit while host orchestration tools remain bionic-native.

## 13.17 Sysroot

A sysroot is a build-time reference tree that acts as a target filesystem base for headers and libraries.

Conceptually:

```text
sysroot/
├── usr/include
├── usr/lib
└── lib
```

The compiler/linker can be directed to search target paths relative to this tree rather than the build host’s `/usr`.

A sysroot is not identical to a runtime rootfs, though a target rootfs can sometimes serve as a sysroot input.

## 13.18 Native and cross compilation

### Native build

```text
build machine == runtime target architecture/environment
```

### Cross build

```text
build machine/environment
    !=
runtime target
```

Example:

```text
host orchestration: Termux bionic Python/Meson/Ninja
compiler target: glibc AArch64 world
runtime target: glibc Mesa/Turnip on Android kernel
```

Cross builds must distinguish tools that run **during the build** from binaries that run **on the target**.

## 13.19 Build, host, target terminology

GNU-style terminology can be summarized as:

```text
build
    machine where the build runs

host
    machine/environment where the produced program runs

target
    architecture/platform for code generated by a compiler-like tool
```

For normal application cross compilation, build and host are often the key distinction. For building compilers, all three become important.

## 13.20 Configure tests in cross builds

A build system may try:

```text
compile test program
    -> execute test program
    -> inspect result
```

In a cross build:

```text
host tool machine: bionic environment
produced test: glibc target binary
```

The test cannot necessarily run directly under the build tool’s default assumptions.

Cross files, wrapper commands, emulation strategies, or predeclared properties may be needed.

## 13.21 Build tree, install tree, runtime tree

Keep these distinct.

```text
source tree
    -> source and build definitions

build tree
    -> objects, generated sources, temporary tests, final build artifacts

staged install tree
    -> files arranged as installation payload

runtime tree
    -> promoted artifacts plus runtime state/providers
```

Mixing them makes provenance and cleanup difficult.

## 13.22 `PREFIX` and `DESTDIR`

A useful packaging model:

```text
PREFIX=/usr
DESTDIR=/tmp/pkgroot
```

stages:

```text
/tmp/pkgroot/usr/bin/app
```

while preserving the logical installation path `/usr/bin/app`.

This is valuable for inspecting what a project would install without mutating the live environment.

## 13.23 Project-specific build worlds

A useful model is:

```text
World A: Termux bionic-native builds
World B: Android NDK target builds
World C: Debian/glibc reference builds
World D: project glibc target builds
```

Each should have explicit:

```text
compiler target
headers
libraries
pkg-config universe
sysroot/search policy
runtime validation target
```

The main risk is accidental cross-world contamination.

## 13.24 Practical debugging ladder

When a build fails:

```text
1. Is configuration using the intended compiler?
2. Are headers from the intended world?
3. What does pkg-config return?
4. Which linker is invoked?
5. Which libraries are selected?
6. What interpreter and RUNPATH are in the output?
7. Which symbol versions are required?
8. Does the produced binary run in the intended runtime world?
```

Capture verbose build commands when possible.
